# UC2 Xbox calling-convention audit

The main audit below covers the custom argument-location overrides in `config/uc2.toml`. A focused runtime-path audit is also included for the guest thread and wait calls observed during the first match-load attempt.

## Method and limits

XboxXBERecomp's `xbe_symbols` scanner was run against the local `default.xbe` using the XDK 5849 signatures. It identified 13 LTCG D3D entry points whose register-use shape or callee stack-pop size differs from the reference library. The generated `x86_recomp.*.cpp` files preserve the title's call-site register moves and stack pushes, which are the primary evidence for UC2's argument locations. The corresponding runtime HLE definitions show how those mapped arguments are consumed.

The scanner reports registers read before being overwritten and the callee's stack-pop size. It does not identify API argument meaning or ordering. Therefore, matching register sets alone is not treated as a complete ABI proof. Runtime behavior currently verifies device creation and sustained D3D execution, but has not yet verified visible gameplay.

## Overrides

| Function | Mapping in API argument order | Evidence and status |
|---|---|---|
| `CDevice_KickOff` | `edx` | At `0x003868F4`, the guest moves the device pointer from ESI to EDX before the call. The runtime HLE ignores the argument. Location verified; semantic use is not exercised by the HLE. |
| `D3D_InitializeDevicePushState` | `esi` | At `0x0038B0B1`, the caller moves the device pointer from EBP to ESI before calling `0x003867A0`; the callee dereferences the device through ESI. Directly verified. |
| `D3DDevice_DrawVertices` | `stack`, `ecx`, `eax` | At `0x00201488`, the caller pushes EBP and calls with ECX and EAX live. EBP is the primitive. In the guest callee at `0x00385800`, `mov edi,eax` feeds a loop that decrements the count in `0x100`-vertex chunks, while `mov ebx,ecx` seeds and advances the vertex source value. The HLE argument order is therefore primitive, start, count, matching stack, ECX, EAX. |
| `D3DDevice_SelectVertexShader` | `eax`, `ebx` | At `0x00208148`, EAX carries the selected handle and EBX is zero for the slot. The HLE consumes handle then slot. Directly supported by the call site. |
| `D3DDevice_SetIndices` | `ebx`, `stack` | At `0x00207372`, EBX is live and the caller has pushed the second argument. The guest body stores EBX as the index buffer and the stack argument as the base vertex. Directly supported by the callee. |
| `D3DDevice_SetPixelShaderConstant` | `ecx`, `stack`, `eax` | At `0x0020827B`, ECX is the first register argument, a data pointer is pushed, and EAX carries the final value argument. The HLE consumes register, data, count in that order. Directly supported. |
| `D3DDevice_SetRenderTargetFast` | `stack`, `ebx`, `eax` | At `0x001FEF52`, the caller pushes the first argument and supplies EBX/EAX for the remaining arguments. The guest callee reads the first argument from the stack; the HLE uses the first two arguments as render and depth targets and ignores flags. Locations are supported; the ignored flags value is not runtime-validated. |
| `D3DDevice_SetStreamSource` | `eax`, `ebx`, `stack` | At `0x002081DA`, EAX is the stream number, EBX the vertex buffer, and the caller-pushed value is the stride. The HLE consumes stream, buffer, stride. Directly supported. |
| `D3DDevice_SetTransform` | `eax`, `edx` | At `0x0038AE97`, EAX is the transform index and EDX points to the matrix. Directly supported. |
| `D3DDevice_Swap` | `eax` | The scanner reports EAX as the title's register argument. The HLE ignores the value; its semantic meaning is not runtime-validated. |
| `D3DResource_IsBusy` | `ecx` | At `0x00030170`, the resource pointer is loaded into ECX before the call. The HLE consumes that resource pointer. Directly supported. |
| `D3D_InternalRelease` | `esi` | At `0x003816D6`, the object pointer is loaded into ESI before the call. The HLE consumes the object pointer. Directly supported. |
| `DSOUND_Export_B0098` | `edi`, `stack`, `stack` | At `0x00365147`, the worker calls with EDI and two pushed arguments. The HLE uses the first two as stream and packet data; the final completion argument is not used by this implementation. Locations match the worker call. |
| `D3D_MakeRequestedSpace` | `eax`, `stack` | The scanner reports one EAX register argument and one stack argument. At `0x003839D7`, ECX is pushed; the runtime HLE ignores both values and allocates scratch push space. Location shape is verified; value semantics are not exercised by the HLE. |
| `Direct3D_CreateDevice` | `edx`, `ebx`, `esi`, `eax`, `stack`, `ecx` | The title call at `0x00019591` uses this mixed register/stack form. The fifth argument, presentation parameters, is read from the mapped stack slot by the HLE; the resulting runtime log reports the expected 640x480 parameters. This validates that argument's location and value. The other arguments are not all consumed or runtime-validated by the HLE. |

`stack` means the next stack argument slot in API order; the mapped wrapper accounts for stack cleanup according to the title's callee convention.

## File-read ABI evidence

At guest call site `0x00262C22`, UC2 calls the kernel thunk for ordinal 219 (`NtReadFile`). Immediately before the call, it pushes these eight arguments in reverse order: file handle from `[ebp-0x08]`; null event, APC routine, and APC context; an I/O status block at `[ebp-0x20]`; buffer at `[ebp-0x22C]`; length `0x200`; and a byte-offset pointer at `[ebp-0x18]`, initialized to `0x800`. The generated call enters `x86_kernel(..., 219)`. XboxXBERecomp registers ordinal 219 as an eight-argument stdcall export, reads argument `i` from `esp + 4 + 4*i`, and returns by popping eight arguments. The file HLE reads the same eight slots in the documented order. This call-site and wrapper evidence supports the `NtReadFile` ABI mapping; it does not prove that the match-load path reaches this or another read call.

Generated-code cross-check: UC2 has seven direct calls to ordinal 219, returning at `0x002624B1`, `0x00262668`, `0x002626AD`, `0x00262C28`, `0x00268050`, `0x00322B4A`, and `0x003896A1`. Each pushes eight arguments before `x86_kernel(..., 219)`. At the newly instrumented call `0x00322B44`, the stack arguments are handle `[ebp+8]`, three null completion arguments, IOSB `[ebp-0x10]`, buffer `[ebp-0x210]`, length `0x200`, and offset pointer `[ebp-8]`. At `0x0038969B`, they are handle `ecx`, three null completion arguments, IOSB `0x00394748`, buffer `eax`, length `esi`, and offset pointer `0x00394778`. These two sites use the same eight-slot stack ABI as the `0x00262C22` example; no register-passed kernel arguments are present.

The file HLE now records `FILE_SYNCHRONOUS_IO_ALERT`/`FILE_SYNCHRONOUS_IO_NONALERT` from the open options. It still transfers bytes inline, but for successful I/O on an asynchronous handle it writes a completed IOSB and signals the file object/event, then returns `STATUS_PENDING`. This lets UC2's pending-read path wait on the file handle and inspect the IOSB as it does on Xbox. Traced Aqueduct opens now include their option bits and synchronous/asynchronous classification, so the next run can confirm this path is being selected. The transfer itself is not yet dispatched asynchronously on a host worker, and this change has not yet been validated in a match-load run.

## Kernel I/O dispatch ABI evidence

Static call-site inspection confirms the calling conventions for UC2's imported I/O dispatch routines. At `0x00318306`, the XNET caller places the device object in ECX and the IRP in EDX before calling `IofCallDriver`, matching XboxXBERecomp's two-register fastcall handler. XPP call sites such as `0x0039C174`, `0x0039C1CD`, and `0x0039C410` place the IRP in ECX and zero in EDX before calling `IofCompleteRequest`, matching its fastcall mapping. Nearby instructions write IRP status and information at offsets `+0x10` and `+0x14`.

At `0x0039C187`, XPP pushes key `0`, IRP from ECX, then device object from EDI before calling `IoStartPacket`; this is the expected right-to-left stack order for ordinal 83's three arguments. At `0x0039C1D5`, it pushes one device-object pointer before `IoStartNextPacket`, matching ordinal 81's one stack argument. These mappings are supported by disassembly, not by runtime execution. The XPP initialization helper at `0x00395879` pushes six stack arguments to `IoCreateDevice`, matching ordinal 65's six-argument HLE. It tests the returned status at `0x0039587F` and exits the creation loop on a negative result at `0x00395881`; XboxXBERecomp currently returns `STATUS_UNSUCCESSFUL`. The new `0042-trace-uc2-iocreatedevice.patch` logs all six raw arguments and the caller so a match-load run can establish whether this failing path is active. Until that trace shows it is reached, the packet and completion calls may belong to an inactive peripheral-device path and are not tied to the match-load stall.

## Current conclusion

The mappings above have a mixture of direct call-site evidence and partial runtime evidence. They should remain explicit in the title config because the executable's D3D8 library is LTCG and does not follow the reference library's default convention. A rendered gameplay frame and follow-up run are still needed to validate the draw path end to end.

## Match-load thread and wait path

The 08:00 diagnostic log reports guest thread `0x34` starting through routine `0x00267335`, with start routine `0x0002E780` and context `0x017D0000`. The XBE instructions at `0x00267335` push the context argument at `[ebp+0x0C]` and call the start routine at `[ebp+0x08]`. The start routine at `0x0002E780` loads that one stack argument into ESI, calls `0x002EA50`, and returns with `ret 4`. This is a one-argument callee-cleanup handoff.

XboxXBERecomp's `PsCreateSystemThreadEx` handler passes `{start_routine, start_context}` to the guest system routine. `CallGuest` pushes its argument array in reverse order, matching the x86 stack layout above. The host handoff and guest thread startup convention therefore agree for this observed thread.

At `0x002EA99`, the loading worker pushes a timeout, `waitAll = 0`, a two-handle array, and count `2`, then calls the four-argument wrapper at `0x0026686B`. That wrapper supplies `alertable = 0` and calls `0x00266787` with five stack arguments. The latter copies the handles, converts the timeout, then calls thunk VA `0x0039D564`; the XBE thunk value is `0x800000EB`, importing ordinal 235, `NtWaitForMultipleObjectsEx`. Its six arguments are count, handle array, wait type, processor mode `1`, alertability, and timeout pointer. The HLE consumes the corresponding slots and ignores processor mode, matching the guest wrapper's setup. No calling-convention mismatch is evident on this startup/wait path.

This trace does not yet identify why match loading stops. A later run with the expanded wait trace showed thread `0x18` starting at guest routine `0x000671F0` with context `0x00587A70`. It waited on event body `0xB0000C40` from 1.397s until the title advanced at 30.374s, then opened `CTF-Downfall.lin`, `CTF-Downfall.xpr`, `_pb.xpr`, and `_uma.xpr`. It entered another wait on the same event immediately afterward. The guest caller at `0x00266766` is a wrapper around `NtWaitForSingleObjectEx`; this may be the title's event loop and is not, by itself, evidence of the level-load stall.

The 13:28 run showed no successful reads from those four level packages before the window was closed at 59.532s. That observation alone did not prove that the guest issued no reads: the earlier transfer trace returned `STATUS_INVALID_HANDLE` without logging the failed request. Commit `0137240` added rejected-transfer logging and guest stacks; commit `d609154` added handles to successful-open records so reads can be correlated with the package that owns each handle. The 13:28 log predates both handle-correlation changes and cannot settle the question. The instrumented binary was rebuilt after `d609154`, but it still needs to run through the match-load transition before the file-I/O path can be concluded.

The longer 13:12 run provides one more clue. At 118.887s, thread `0x18` opened the same four CTF-Downfall packages. At 119.000s, thread `0x38` started through the guest thread wrapper with start routine `0x0002E780` and context `0x01794378`. Sampled waits from that thread were two-object, wait-any calls with a relative timeout of `-280000` 100-ns units (28 ms); each sampled call returned `STATUS_TIMEOUT` (`0x00000102`) through the final sample, entered at 161.358s and returned at 161.386s. The old trace only logged the first wait object's type/body (`Event` at `0xB016F850`), and did not log package reads or the second object. This is consistent with a guest worker polling while its work remains pending, but it does not show why the work remains pending or whether the worker is the level loader.

The next diagnostic build lowers the sampled relative-wait threshold to 10 ms. Since each guest thread logs only its first eight qualifying waits and then every 64th, a 28 ms worker poll remains observable without recording every iteration. This should show the worker's complete wait-any object list and whether its sampled waits time out or complete during the current match-load attempt.

The instrumented runtime logs the Xbox path, host path, file size, and returned handle for each CTF-Downfall package, character animation, and selected character, font, HUD, and UI texture package open, along with the guest stack at the open call. It logs read/write handle, offset, requested and actual byte counts, and status for transfers from those packages; rejected transfers also include a guest stack. Use `./scripts/run-diagnostic.sh` to launch the repo build; it stays open until manually closed. The launcher records the executable path and SHA-256 in each log, which distinguishes traces from older binaries.

The current evidence therefore verifies that the frontend is rendering and that the title reaches the animated match-loading screen, but not that a level has rendered. The ABI audit remains incomplete until a current file-I/O trace identifies whether UC2 reads the packages through valid handles and the runtime reaches a gameplay frame.

The character-select capture `131428_975_4751` narrows the rendering issue: its frame record contains 38 draws. One is a 30-vertex draw using vertex shader handle `B010C131`; one composites the render target; the remaining 36 use the screen-space UI shader `B010C151`. The selected character preview is black in the corresponding framebuffer. The performance sample at 91.083s also reports 38 draws per frame (all 38 raw), matching the captured draw count. This gives no indication that the Vulkan backend dropped a model draw on that captured frame: no skeletal-character draw was submitted. It does not tell whether UC2 failed to read/instantiate the mesh or chose not to submit it; the new trace of `K_Male.ukx` and character-skin assets should distinguish the asset-read part of that path.

The 15:00:23 run (`diagnostic_logs/xberecomp_20261111_150023.log`) reaches the same point on CTF-Aqueduct at 25.351s. The runtime opens `CTF-Aqueduct.lin` (handle `0x1A24`), `CTF-Aqueduct.xpr` (`0x1A28`), `_pb.xpr` (`0x1A2C`), and `_uma.xpr` (`0x1A30`), all with the expected nonzero sizes. It records no successful or rejected transfer for any of those package handles before the window closes at 78.707s. The main guest thread waits on event body `0xB0000C40` at 1.275s, wakes successfully after the event is set at 1.360s, then waits again at 1.384s and wakes at 25.350s. It opens the four Aqueduct packages, resets that event, and enters a third infinite wait at 25.351s that does not return before the run ends. Worker thread `0x38` starts at `0x0002E780` with context `0x017A5C50`; it repeatedly waits on event bodies `0xB016F850` and `0xB016F860` with a 28 ms timeout, receiving `STATUS_TIMEOUT` each time. The 68 saved frame captures corroborate a guest loading stall: ten frames around 15:00:38–48 contain eight draw records, while the later captures remain on the loading image; the 15:01:41 capture contains only a clear and one full-screen quad using texture `0x8333C000`. The renderer is presenting the loading image, with no map scene draws reaching it. This establishes the main thread's immediate blocking point after the package opens, but does not prove why UC2 does not issue package reads or signal the event again. The next Xemu comparison needs to record the main thread's wait and every set/reset of its event as the game proceeds into Aqueduct.

The Xemu reference run on 2026-11-11 (`diagnostic_logs/xemu_20261111_150730.log`, guest trace `diagnostic_logs/xemu_guest_20261111_150735.log`) reached the selected level; the user confirmed being in the level and about to play briefly before closing Xemu. The trace contains 19,717 lines: 751 successful file opens, 33 `STATUS_OBJECT_NAME_NOT_FOUND`, one `STATUS_OBJECT_PATH_NOT_FOUND`, and one `STATUS_SHARING_VIOLATION`; among the five instrumented `NtReadFile` sites, returns include 3,642 `STATUS_SUCCESS`, 2,633 `STATUS_PENDING`, and six `STATUS_END_OF_FILE`. Static inspection of generated XBE code found two more direct `NtReadFile` sites at `0x00322B44` and `0x0038969B`; the old trace did not cover them, so its I/O counts and lack of package-read evidence are incomplete. The match workers at contexts `0x005914E0` and `0x017BE740` each woke with `STATUS_WAIT_1` twice, meaning the second handle in each wait-any pair was signaled. The old breakpoint logged only nonzero returns from `sub_2E310`, and it recorded none; it therefore did not reveal what the worker did after those wakes. This establishes that the reference worker receives signals and UC2 reaches gameplay, unlike the recomp's repeated `STATUS_TIMEOUT` samples during its Aqueduct loading stall. The old trace's NtCreateFile path pointers are all null because it inspected the wrong stack slot after the call. Static disassembly shows the wrapper overwrites `[EBP+8]` with a trailing-separator flag but retains the original path in the local `ANSI_STRING` Buffer field at `[EBP-8]`; the current script reads that frame-local pointer, logs zero and nonzero `sub_2E310` returns, and covers all seven direct read call sites. These changes still need a live run.

The two additional `NtReadFile` sites also match the export's eight-stack-argument ABI (ordinal 219):

| Guest call site | Arguments in API order | Return handling |
| --- | --- | --- |
| `0x00322B44` | handle `[EBP+8]`; event/APC/APC context `0`; IOSB `EBP-0x10`; buffer `EBP-0x210`; length `0x200`; offset pointer `EBP-8` | Accepts any nonnegative NTSTATUS, including `STATUS_PENDING`. |
| `0x0038969B` | handle `*(0x394780)`; event/APC/APC context `0`; IOSB `0x394748`; buffer `*(EDI+0x8DC)`; length `align_up(*(0x394740), 0x200)`; offset pointer `0x394778` | Accepts any nonnegative NTSTATUS, including `STATUS_PENDING`. |

Both callers push the eight parameters in right-to-left order, matching `KERNEL_EXPORT(219, NtReadFile, 8)`. No stack-arity or argument-order mismatch is evident at these sites. Their acceptance of `STATUS_PENDING` means the remaining concern is the I/O completion behavior and when the guest consumes the destination buffer, not the call convention itself.

A full search of the XBE module disassembly and import labels finds no `NtReadFileScatter` symbol or call site. XboxXBERecomp's scatter-read HLE therefore is not an alternate UC2 map-package read path missing from this trace; ordinary `NtReadFile` calls remain the file-transfer path to follow.

Another caller at `0x002626A7` explicitly waits on the file handle when `NtReadFile` returns `STATUS_PENDING`, then consumes the IOSB at `[EBP-8]`. The Xemu trace script now records that post-wait IOSB status and information count, allowing a reference run to show whether pending reads complete with bytes and whether the file-handle wait returns successfully.

The worker's control flow qualifies those wait results: at `0x2EA70` it examines the previous wait result and context fields at `+0xB4`/`+0xB8` to set `EBX`; after the next wait returns, it calls `sub_2E310` only when that gate is nonzero. So `STATUS_WAIT_1` proves a handle signaled, but by itself does not prove the completion handler ran. The Xemu trace script now records `EBX`, the prior result, the relevant context fields, and entry to the completion call; this will show whether the signaled handle is accepted by the worker's state machine.

The old trace reports that values in the worker's wait pairs also occur as `NtReadFile` handles: `0x18` has 233 pending and 241 successful returns, `0x14` has 23 pending and 159 successful returns, and `0x2C` has 216 pending and 43 successful returns across the captured run. These counts cover five read sites, not the two sites found later. This overlap alone does not identify the waited-on object because the trace did not capture handle creation and closure; a numeric handle may be reused after its earlier object is closed. The reads also frequently return `STATUS_PENDING`, confirming that this run exercises asynchronous I/O.

Static disassembly resolves the worker object type. In `sub_2E8E0`, UC2 calls `sub_26658B` at `0x2E8EE` and `0x2E902` to create two events, stores their returned handles at context offsets `+0x10` and `+0x0C`, then starts the worker at `0x2E780` with that context. The recomp's 15:00 wait trace resolves its corresponding handles to event objects at guest bodies `0xB016F850` and `0xB016F860`, which matches the guest setup. The old Xemu trace's wait results therefore cannot be used to claim that Xemu waits on file objects. The updated Xemu GDB capture records event-creation caller addresses and returned handles, worker waits, event operations, file opens/reads, and `NtClose`; the close sequence will show whether any matching numeric values were reused. No event-type mismatch has been established.

Both worker-event call sites pass wrapper arguments `(0, 1, 0, 0)`. The wrapper converts its second argument to `EventType=0` and forwards the third as `InitialState=0`, yielding two initially nonsignaled notification events. XboxXBERecomp's `NtCreateEvent` handler maps those same NT arguments to `notification=true` and `signal=0`; event initialization therefore matches the XBE call convention.

The first targeted HLE change now mirrors the observed return contract for asynchronous handles while keeping the transfer inline. The recomp's Aqueduct run still has no transfer from the four map-package handles, and the Xemu reference trace did not identify package paths for its pending reads. The next comparison should inspect the newly logged file-open options and successful package reads, plus Xemu's event/APC arguments, before deciding whether full host-asynchronous dispatch or a different loading-path fix is needed.

## XPP completion-event ABI

Static inspection of the XPP asynchronous-completion path at `0x00396529` shows the state record in ESI. It pushes the output pointer `ESI+0x0C`, object-type pointer `[0x0039D540]`, then the handle `[ESI+4]` before calling `ObReferenceObjectByHandle` (ordinal 246). This is the expected right-to-left order for three stack arguments. XboxXBERecomp's ordinal 246 handler reads the handle from argument 1 and writes the referenced guest dispatcher-object address through argument 3. The caller checks the returned NTSTATUS and clears the stored handle and object pointer if the reference fails. The stack shape and output slot match.

Five XPP sites call `KeSetEvent` during asynchronous completion: `0x00395E86`, `0x00396067`, `0x00396BCC`, `0x0039B90F`, and `0x0039BE52`. Each places the dispatcher-object pointer, increment, and wait flag in three stack slots, matching ordinal 145's HLE signature. The HLE resolves argument 1 as a guest dispatcher object and signals it. This verifies the static ABI mapping, but does not establish that these sites signal either UC2 match-worker event during the Aqueduct transition. The existing Xemu gameplay trace predates these targeted breakpoints, and the latest attempted Xemu launch did not initialize SDL; a new successful reference capture is still needed to correlate the XPP object pointer with the worker's second wait handle.

### Offscreen startup run

The instrumented build was run for 25 seconds with `SDL_VIDEODRIVER=offscreen` and `SDL_AUDIODRIVER=dummy` in the restricted diagnostic environment (`diagnostic_logs/xberecomp_20261111_200357.log`). Vulkan presented the textured “Powered by Unreal Technology” screen at about 60 FPS; the captured frame contains one full-screen quad and its expected 640x480 texture. This proves the offscreen path reaches and renders the startup logo, but it does not demonstrate menu or gameplay rendering. The main startup event at `0xB0000C40` was signaled and its waiter returned success. There were no `IoCreateDevice`, `IoStartPacket`, or XPP completion-event log entries during this 25-second run, so the XPP device-creation stub is not on the observed startup-logo path. This does not rule out that path during later gameplay. This run had no input and therefore cannot be compared to the user's interactive Aqueduct load.

# UC2 Xbox calling-convention audit

The main audit below covers the custom argument-location overrides in `config/uc2.toml`. A focused runtime-path audit is also included for the guest thread and wait calls observed during the first match-load attempt.

## Method and limits

XboxXBERecomp's `xbe_symbols` scanner was run against the local `default.xbe` using the XDK 5849 signatures. It identified 13 LTCG D3D entry points whose register-use shape or callee stack-pop size differs from the reference library. The generated `x86_recomp.*.cpp` files preserve the title's call-site register moves and stack pushes, which are the primary evidence for UC2's argument locations. The corresponding runtime HLE definitions show how those mapped arguments are consumed.

The scanner reports registers read before being overwritten and the callee's stack-pop size. It does not identify API argument meaning or ordering. Therefore, matching register sets alone is not treated as a complete ABI proof. Runtime behavior currently verifies device creation and sustained D3D execution, but has not yet verified visible gameplay.

## Overrides

| Function | Mapping in API argument order | Evidence and status |
|---|---|---|
| `CDevice_KickOff` | `edx` | At `0x003868F4`, the guest moves the device pointer from ESI to EDX before the call. The runtime HLE ignores the argument. Location verified; semantic use is not exercised by the HLE. |
| `D3D_InitializeDevicePushState` | `esi` | At `0x0038B0B1`, the caller moves the device pointer from EBP to ESI before calling `0x003867A0`; the callee dereferences the device through ESI. Directly verified. |
| `D3DDevice_DrawVertices` | `stack`, `ecx`, `eax` | At `0x00201488`, the caller pushes EBP and calls with ECX and EAX live. EBP is the primitive. In the guest callee at `0x00385800`, `mov edi,eax` feeds a loop that decrements the count in `0x100`-vertex chunks, while `mov ebx,ecx` seeds and advances the vertex source value. The HLE argument order is therefore primitive, start, count, matching stack, ECX, EAX. |
| `D3DDevice_SelectVertexShader` | `eax`, `ebx` | At `0x00208148`, EAX carries the selected handle and EBX is zero for the slot. The HLE consumes handle then slot. Directly supported by the call site. |
| `D3DDevice_SetIndices` | `ebx`, `stack` | At `0x00207372`, EBX is live and the caller has pushed the second argument. The guest body stores EBX as the index buffer and the stack argument as the base vertex. Directly supported by the callee. |
| `D3DDevice_SetPixelShaderConstant` | `ecx`, `stack`, `eax` | At `0x0020827B`, ECX is the first register argument, a data pointer is pushed, and EAX carries the final value argument. The HLE consumes register, data, count in that order. Directly supported. |
| `D3DDevice_SetRenderTargetFast` | `stack`, `ebx`, `eax` | At `0x001FEF52`, the caller pushes the first argument and supplies EBX/EAX for the remaining arguments. The guest callee reads the first argument from the stack; the HLE uses the first two arguments as render and depth targets and ignores flags. Locations are supported; the ignored flags value is not runtime-validated. |
| `D3DDevice_SetStreamSource` | `eax`, `ebx`, `stack` | At `0x002081DA`, EAX is the stream number, EBX the vertex buffer, and the caller-pushed value is the stride. The HLE consumes stream, buffer, stride. Directly supported. |
| `D3DDevice_SetTransform` | `eax`, `edx` | At `0x0038AE97`, EAX is the transform index and EDX points to the matrix. Directly supported. |
| `D3DDevice_Swap` | `eax` | The scanner reports EAX as the title's register argument. The HLE ignores the value; its semantic meaning is not runtime-validated. |
| `D3DResource_IsBusy` | `ecx` | At `0x00030170`, the resource pointer is loaded into ECX before the call. The HLE consumes that resource pointer. Directly supported. |
| `D3D_InternalRelease` | `esi` | At `0x003816D6`, the object pointer is loaded into ESI before the call. The HLE consumes the object pointer. Directly supported. |
| `DSOUND_Export_B0098` | `edi`, `stack`, `stack` | At `0x00365147`, the worker calls with EDI and two pushed arguments. The HLE uses the first two as stream and packet data; the final completion argument is not used by this implementation. Locations match the worker call. |
| `D3D_MakeRequestedSpace` | `eax`, `stack` | The scanner reports one EAX register argument and one stack argument. At `0x003839D7`, ECX is pushed; the runtime HLE ignores both values and allocates scratch push space. Location shape is verified; value semantics are not exercised by the HLE. |
| `Direct3D_CreateDevice` | `edx`, `ebx`, `esi`, `eax`, `stack`, `ecx` | The title call at `0x00019591` uses this mixed register/stack form. The fifth argument, presentation parameters, is read from the mapped stack slot by the HLE; the resulting runtime log reports the expected 640x480 parameters. This validates that argument's location and value. The other arguments are not all consumed or runtime-validated by the HLE. |

`stack` means the next stack argument slot in API order; the mapped wrapper accounts for stack cleanup according to the title's callee convention.

## File-read ABI evidence

At guest call site `0x00262C22`, UC2 calls the kernel thunk for ordinal 219 (`NtReadFile`). Immediately before the call, it pushes these eight arguments in reverse order: file handle from `[ebp-0x08]`; null event, APC routine, and APC context; an I/O status block at `[ebp-0x20]`; buffer at `[ebp-0x22C]`; length `0x200`; and a byte-offset pointer at `[ebp-0x18]`, initialized to `0x800`. The generated call enters `x86_kernel(..., 219)`. XboxXBERecomp registers ordinal 219 as an eight-argument stdcall export, reads argument `i` from `esp + 4 + 4*i`, and returns by popping eight arguments. The file HLE reads the same eight slots in the documented order. This call-site and wrapper evidence supports the `NtReadFile` ABI mapping; it does not prove that the match-load path reaches this or another read call.

Generated-code cross-check: UC2 has seven direct calls to ordinal 219, returning at `0x002624B1`, `0x00262668`, `0x002626AD`, `0x00262C28`, `0x00268050`, `0x00322B4A`, and `0x003896A1`. Each pushes eight arguments before `x86_kernel(..., 219)`. At the newly instrumented call `0x00322B44`, the stack arguments are handle `[ebp+8]`, three null completion arguments, IOSB `[ebp-0x10]`, buffer `[ebp-0x210]`, length `0x200`, and offset pointer `[ebp-8]`. At `0x0038969B`, they are handle `ecx`, three null completion arguments, IOSB `0x00394748`, buffer `eax`, length `esi`, and offset pointer `0x00394778`. These two sites use the same eight-slot stack ABI as the `0x00262C22` example; no register-passed kernel arguments are present.

The file HLE now records `FILE_SYNCHRONOUS_IO_ALERT`/`FILE_SYNCHRONOUS_IO_NONALERT` from the open options. It still transfers bytes inline, but for successful I/O on an asynchronous handle it writes a completed IOSB and signals the file object/event, then returns `STATUS_PENDING`. This lets UC2's pending-read path wait on the file handle and inspect the IOSB as it does on Xbox. Traced Aqueduct opens now include their option bits and synchronous/asynchronous classification, so the next run can confirm this path is being selected. The transfer itself is not yet dispatched asynchronously on a host worker, and this change has not yet been validated in a match-load run.

## Kernel I/O dispatch ABI evidence

Static call-site inspection confirms the calling conventions for UC2's imported I/O dispatch routines. At `0x00318306`, the XNET caller places the device object in ECX and the IRP in EDX before calling `IofCallDriver`, matching XboxXBERecomp's two-register fastcall handler. XPP call sites such as `0x0039C174`, `0x0039C1CD`, and `0x0039C410` place the IRP in ECX and zero in EDX before calling `IofCompleteRequest`, matching its fastcall mapping. Nearby instructions write IRP status and information at offsets `+0x10` and `+0x14`.

At `0x0039C187`, XPP pushes key `0`, IRP from ECX, then device object from EDI before calling `IoStartPacket`; this is the expected right-to-left stack order for ordinal 83's three arguments. At `0x0039C1D5`, it pushes one device-object pointer before `IoStartNextPacket`, matching ordinal 81's one stack argument. These mappings are supported by disassembly, not by runtime execution. The XPP initialization helper at `0x00395879` pushes six stack arguments to `IoCreateDevice`, matching ordinal 65's six-argument HLE. It tests the returned status at `0x0039587F` and exits the creation loop on a negative result at `0x00395881`; XboxXBERecomp currently returns `STATUS_UNSUCCESSFUL`. The new `0042-trace-uc2-iocreatedevice.patch` logs all six raw arguments and the caller so a match-load run can establish whether this failing path is active. Until that trace shows it is reached, the packet and completion calls may belong to an inactive peripheral-device path and are not tied to the match-load stall.

Further disassembly narrows this `IoCreateDevice` loop to memory-unit devices: it initializes names from `\Device\MU_0` / `\Device\MU_%x`, iterates up to eight slots, requests a `0x170`-byte device extension, and fills that extension with the device object, slot index, and memory-unit flags before calling `0x0039BCD0`. This is not evidence that the map loader's hard-disk reads use these devices. The `STATUS_UNSUCCESSFUL` stub may disable memory-unit support, but it is not currently a justified match-load fix; keep it instrumented and prioritize the map file-open/read caller trace.

## Current conclusion

The mappings above have a mixture of direct call-site evidence and partial runtime evidence. They should remain explicit in the title config because the executable's D3D8 library is LTCG and does not follow the reference library's default convention. A rendered gameplay frame and follow-up run are still needed to validate the draw path end to end.

## Loader, input worker, and profile findings

### Ghidra correction: `0x2E780` is the XInput worker

The local Ghidra project was opened read-only with Ghidra 12.2. Its decompilation shows that `0x2E780` only forwards to `0x2EA50`; `0x2EA50` waits on the two handles stored at context offsets `+0x10` and `+0x0C`; and `0x2E310` calls `XGetDeviceChanges`, `XInputOpen`/`XInputClose`, and `XInputGetState`. This is UC2's controller polling worker, not the map loader or an async file-completion worker. The guest event bodies `0xB016F850` and `0xB016F860`, the 28 ms wait timeouts, and the `WAIT_1` results therefore do not explain the Aqueduct load stall. The `NtSetEvent(handle=0x14)` observed at `0x2E2EE` is consistent with the separate worker-stop/join helper at `0x2E2D0`.

Earlier notes in this audit and the Xemu trace script called this a “match-load worker” and treated `sub_2E310` as a completion handler. Those conclusions were wrong and are superseded here. The wait ABI itself remains consistent: the wrapper passes a two-handle wait-any call with a relative timeout, and the XInput worker creates two initially nonsignaled notification events. The trace script now labels these as input-worker events so they are not confused with file I/O.
